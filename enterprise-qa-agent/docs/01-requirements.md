# 用户、目标、范围和成功标准

## 业务目标

员工询问制度或产品问题，系统必须给出可追溯的原文依据、版本和资料缺口。正确拒答、列出冲突和追问也属于有效处理结论；不能为了给出唯一答案而隐藏冲突或编造引用。

输入为问题和可选对话历史。资料是带 ID、版本日期和片段 ID 的合成 FAQ/制度。两个业务工具分别检索文档定位器、读取原文；第三个控制工具提交回答决策与引用。输出为答案、文档/版本/原文引用、缺口、追问和任务状态。

## 验收标准

| 必验点 | 可检查标准 | 真实记录 |
|---|---|---|
| 明确答案 | 先读原文，再依据完整片段回答，引用支持事实 | clear_answer/ |
| 文档冲突 | 同时引用 D01 的 30 天和 D02 的 15 天，补查范围/优先级并请求确认，不选较新文档作结论 | conflict/ |
| 资料外问题 | 改写或补充检索后说明缺口，不用常识回答天气问题 | outside_corpus/ |
| 改写相似问题 | “票据最迟啥时候交”经过查询改进，得到单制度下同样的 30 天答案 | paraphrase/ |
| 上下文追问 | 有年假用户前文时恢复主题，无前文时先澄清；历史助手事实不作为证据 | context_followup/、context_missing/ |
| 工具失败 | 一次失败可观察后重试；持续不可用时明确失败，不凭搜索标题作答 | search_failure_once/、read_failure_once/、permanent_failure/ |

以上目录均位于 examples/live/。扩展验证包括：仅 D01 无冲突回答 30；替换原文为 45 后更新答案；冲突被资料更新消除后正常回答；读取后来源变化时拒绝旧引用并重读；步骤上限时明确未完成。

## 强制边界

- 检索命中不是引用证据，必须实际读取。引用包含文档 ID、版本日期、片段 ID 与完整原句。
- 不能截取数字而丢失单位、否定或适用条件；不能把另一文档的句子借给当前 ID。
- 同一控制主题的当前原文有不同说法时，不根据日期或模型偏好自行裁定。未读取的冲突说法也不能被忽略。
- 历史只帮助理解指代，不证明事实。没有相关原文时返回缺口。
- 来源更改后旧内容哈希失效；即使同日期也必须使用新原文。

## 范围取舍

优先 3 小时建议范围内的闭环，采用 CLI、小型 JSON 语料和人工主题词表，不做界面、PDF/OCR、互联网搜索、企业账号权限或向量服务。回答采用抽取式事实，模型选择决策和证据，程序负责校验与呈现，不声称已经具备任意问题的语义蕴含判断能力。
