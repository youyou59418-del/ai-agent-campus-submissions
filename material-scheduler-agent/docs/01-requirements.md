# 需求、范围和成功标准

## 用户和业务目标

用户是内容运营与审核团队。运营人员给出素材 ID、渠道和发布时间要求，系统从合成素材库读取元数据、执行规则、检查已有排期，形成可审核的草稿。目标是减少人工查资料和反复找时间的工作，同时让风险、确认权限与实际保存结果可追溯。

一次输入可包含 1～10 项素材。输入包含稳定的请求 ID、每项素材 ID、北京时间的整点发布时间、是否为硬性时间要求、渠道，以及可选的用户已确认时段。元数据、补充资料、规则和已有排期位于 `data/`。

## 核心约束

1. 硬性要求不能由模型修改。替代时段保存为建议；未经用户同意保持待确认。
2. 缺资料先尝试补查，仍不足则返回待补字段。版权未确认阻断；出镜授权不明确转人工审核。这些是合成规则，不代表真实平台政策。
3. 保存前必须完成读取、审核和可用性查询，保存时重新检查冲突。
4. 同请求同素材只产生一份草稿；用户确认和旧草稿因新占用而改期均更新同一草稿 ID。
5. 保存异常明确返回失败。没有发布工具，所有结果 `published=false`。
6. 模型每一步选择工具，工具结果返回给模型。步数上限后明确 `INCOMPLETE / STEP_LIMIT`。

## 验收表

| 验收点 | 可检查的成功标准 | 验证入口 |
|---|---|---|
| 正常排期 | 审核通过、原定空闲时间保存为 READY_DRAFT、未发布 | `examples/mock/normal/` |
| 信息缺失 | 补查后仍缺资料，返回 NEEDS_INFO 和缺失字段，无草稿 | `examples/mock/missing/` |
| 规则风险 | 版权风险 BLOCKED；出镜授权不明 NEEDS_REVIEW；均不保存 | `examples/mock/blocked/`、`risk_review/` |
| 时段冲突 | 18:00 占用，查询替代时间，19:00 仅为待确认建议，保留原要求 | `examples/mock/conflict/` |
| 重复提交 | 两轮使用同数据库，草稿 ID 一致，行数为 1 | `examples/mock/duplicate/` |
| 保存失败 | 注入存储故障，outcome=SAVE_FAILED、draft_save_status=FAILED，行数为 0 | `examples/mock/save_failure/` |
| 更换占用并重复 | 第二轮占用先前建议时段，重新建议其他时间，ID 不变、仍待确认 | `examples/mock/changed_occupancy/` |
| 确认边界 | 仅用户输入的确切 approved_slot 可批准替代时段；模型伪造参数被拒绝 | `examples/mock/confirmed/`、工程测试 |
| 模型动态决策 | 至少两条真实模型路径，观察不同结果后选不同动作 | 已完成，`examples/live/normal/`、`conflict/`、`missing/` 等实际模型记录 |

以上 Mock 材料仅验证业务流程。同名的 `examples/live/` 已使用 `qwen3.8-27b` 完成 13 组真实模型场景；评审应优先核对真实 Trace。各目录的实际行数和重复草稿 ID 记录在场景摘要中。

## 范围取舍

采用 CLI 和本地函数工具，优先核心闭环。素材读取与审核基于合成元数据，未实现视频内容安全分类；已有排期为 JSON，草稿为 SQLite。没有界面、线上部署、多 Agent、发布系统或生产级 Runtime。采用单 Agent 可以直接观察其根据返回结果的动作变化，避免把时间投入题目未要求的基础设施。
