# 工程复盘、学习与下一步


## 最难的问题：把建议、确认和保存分开

模型选出一个可用时间，不代表用户允许改变硬性要求；工具返回成功，也不代表真实发布。实现上保留 requested_slot，将 suggested_slot 单独保存，由程序依据用户输入生成确认状态。最终报告只使用工具和数据库事实。测试让模型伪造 confirmed 参数、跳过审核、调用 publish 或提前 finish，检验这些边界是否仍被守住。

## 幂等需要考虑后续状态

简单“存在就返回”会遗漏用户后续确认、旧时段新增占用和要求被改变三种情况。现在同键同要求返回同一记录；精确确认可升级草稿；旧时间失效可以重排并递增 revision；要求改变则拒绝复用旧键。已确认的旧时间不会自动批准新的时间。并发测试进一步检查了数据库唯一键和事务，而不仅检查顺序执行。

## 本次失败带来的认识

模型接入区分网络、鉴权、可调用性与业务完成四个层次；验证以实际工具状态与保存结果为准，不能把服务连通当成业务完成。

随后使用 qwen3.8-27b 跑通模型调用。首次批次暴露了离线测试没有发现的问题：模型把“更改硬性时间需确认”理解成“未确认不能保存建议草稿”，在冲突与重复提交时提前 finish。修正提示词并新增 finish 未完成项检查后，全套真实重测 13/13 通过。修正前 Trace 保留在 examples/live-before-fix/，体现学习与修改的依据。

58 项工程测试和 13 组离线场景证明本地逻辑；真实模型的 13 组场景提供了另外的模型决策证据。二者不能混为同一个成功率。免费额度路由目前仅离线模拟验证，实际运行按用户最新要求固定模型，额度不足由用户更换；没有为了验证路由而主动耗尽额度。

## 当前可解释的取舍

原生循环足以展示核心决策，不引入框架和多 Agent，减少安装和概念负担。SQLite 适合单机事务；合成 JSON 便于评审修改占用时段，但没有跨系统事务能力。候选窗口限制便于审计和约束步数，代价是不能自动搜索全天或跨天。这些限制在需求与评估文档中明确列出。

## 下一步
按优先级

1. 扩大合成测试之外的评估，加入更复杂的多素材窗口和对抗输入，不用当前 13 个样例推断生产效果。
2. 若继续扩展业务，再加入确认身份、草稿过期回收、排期服务的原子预留，以及真实素材内容审核。它们不是本次已完成能力。
